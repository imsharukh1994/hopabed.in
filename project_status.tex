\section{PayU End-to-End Payment Flow Specification}

\subsection{Hash Verification Standard}
PayU signatures use SHA-512 hashing:
\begin{equation}
\text{hash} = \text{sha512}(\text{key} \mid \text{txnid} \mid \text{amount} \mid \text{productinfo} \mid \text{firstname} \mid \text{email} \mid \text{udf1} \dots \text{udf5} \mid \text{salt})
\end{equation}
Reverse hash validation on webhook receipt:
\begin{equation}
\text{reverse\_hash} = \text{sha512}(\text{salt} \mid \text{status} \mid \dots \mid \text{udf1} \mid \text{email} \mid \text{firstname} \mid \text{productinfo} \mid \text{amount} \mid \text{txnid} \mid \text{key})
\end{equation}

\subsection{Idempotency \& Security Protocols}
Webhooks process transactions idempotently: if a transaction has already been marked as \texttt{captured}, subsequent duplicate webhooks return HTTP 200 without duplicate execution. Invalid hashes trigger immediate rejection.

\section{MongoDB Concurrency \& Overbooking Security Specification}
To ensure zero double-bookings under high concurrent load, room reservation uses Mongoose optimistic concurrency locking:
\begin{verbatim}
const room = await Room.findOneAndUpdate(
  { _id: roomId, inventoryCount: { $gte: requiredRooms }, __v: currentVer },
  { $inc: { __v: 1 } },
  { new: true, session }
);
\end{verbatim}
If another request modifies inventory concurrently, the \texttt{\_\_v} mismatch prevents overbooking.
